# Автоматизация управления уязвимостями (MaxPatrol VM ↔ Jira) v3.7

## 1. Обзор проекта
Система реализует замкнутый цикл (**Closed-Loop**) управления уязвимостями, объединяя возможности сканера **MaxPatrol VM**, базы активов **Jira Assets (Insight)** и системы обработки заявок **Jira Service Desk**.

**Основная цель:** Полное исключение ручного труда при рассылке отчетов владельцам систем и автоматизация контроля устранения уязвимостей.

---

## 2. Бизнес-логика (Workflow)

Процесс разделен на быстрые ежедневные операции (контроль и обратная связь) и ресурсоемкую еженедельную рассылку:

### 1. Ежедневный цикл (Feedback & Guard Loop)

Выполняется ежедневно для обеспечения актуальности данных и предотвращения потери задач.

* **Поиск и фильтрация:** Скрипт находит все дочерние задачи в Service Desk (статусы `User Action` и `Waiting for support`).
* **Защита от закрытия (Admin Guard):**
    * Скрипт проверяет последний комментарий в каждом тикете.
    * Если обнаружено предупреждение от **Admin** о закрытии из-за отсутствия ответа (7-дневный ультиматум), проверка уязвимостей приостанавливается, значит у человека возник вопрос в тикете, **ISP** отправляется критический алерт для ИБ-специалиста.
    * **Динамический трекинг дедлайнов (Countdown Tags):** На основе даты публикации ультиматума скрипт вычисляет остаток дней и вешает на зонтичную задачу ISP соответствующую метку (`ИБ_7_дней` ... `ИБ_1_дней`) для выстраивания жесткого приоритета на Kanban-доске. Вчерашние теги отсчета автоматически зачищаются.
* **Контроль регламентных автозакрытий (Regulation Guard):** Скрипт проверяет цепочку комментариев на сервере Jira SD. Если обнаружено, что тикет закрылся системным ботом по регламенту (`Issue has been Completed automatically according to Service Regulations`) без промежуточного ответа со стороны ИБ, на родительскую задачу ISP вешается критическая метка `SD_closed_without_answer` и отправляется детальный алерт с перечислением номеров упущенных задач.
* **Интеллектуальный аудит (для тикетов без алертов):**
    * **Сбор данных:** Из задачи скачивается CSV, извлекаются ID уязвимостей и запрашивается их статус в MaxPatrol VM.
    * **Сравнение дат (Time-Sync):** Скрипт сравнивает дату последнего сканирования хоста (`@audittime`) с датой перевода задачи в статус `User Action`. Это исключает закрытие тикета на основе старых данных сканера.
* **Автоматические действия:**
    * ✅ **Автозакрытие:** Если все уязвимости исправлены и аудит подтвержден после даты фиксации.
    * ❌ **Реджект (Return to Work):** Если найдены активные уязвимости — возврат владельцу с инструкцией по перепроверке артефактов и возможностью запроса помощи у ИБ.
    * ⏳ **Ожидание:** Если сканер еще не обновил данные, задача остается в текущем статусе без изменений.
* **Умное тегирование просрочек (Escalation Tags):** При длительном нахождении задач в статусе эскалации скрипт ежедневно проверяет временные диапазоны. На задачу ISP вешаются метки `60d_without_progress`, `80d_without_progress` или `90d_without_progress`. При переходе на новый этап или выходе из эскалации неактуальные метки зачищаются модулем `tags_isp.py` для сохранения порядка на доске.
* **Сводная отчетность в ISP:** В родительскую задачу еженедельного среза ежедневно пишутся отчеты:
    * **Action Report:** Список закрытых и возвращенных задач.
    * **Admin Alert:** Список тикетов, требующих немедленного ответа ИБ.
    * **Scan Alert:** Задачи, зависшие в `User Action` > 14 дней (проблемы со сканированием).
    * **SLA Escalation:** Задачи, находящиеся в поддержке ровно 60, 80 или 90 дней (строго точечное информирование один раз за контрольную точку без ежедневного спама).


### 2. Еженедельная рассылка (Monday Action)
Запускается по понедельникам для формирования нового фронта работ.

*   **Full ETL:** Полный сбор данных из MP VM по всем PDQL-запросам (`intergrations/jira-pdql/`).
*   **CMDB Enrichment:** Обогащение данных через **Jira Assets (Insight)**: определение владельцев (Owner), ИТ-систем и ответственных.
*   **Организация задач:** 
    *   Создание главной задачи в Jira Core (**ISP**) — «зонтика» для всей недели.
    *   Создание персональных тикетов в **Service Desk** для каждого владельца системы.
    *   **Табличная визуализация:** В описание тикета встраивается Wiki-таблица со связкой `Хост | ИТ Система | Список CVE или Краткое описание уязвимости`.
    *   **Отчетность:** Формирование и прикрепление детализированных XLSX и CSV (Whitelisted) отчетов.

```
  [ MaxPatrol VM ]             [ Python Orchestrator (Main) ]          [ Jira (Core & Service Desk) ]
                                      (isd-automation)

         |                                   |                                       |
         |      (1) EXTRACT (Извлечение)     |                                       |
         |<--------------------------------->|                                       |
         |       PDQL Data (timeout 180s)    | [ .env ] [ intergrations/ ]           |
         |                                   |                                       |
         |      (2) ENRICH (Обогащение)      |          (3) CMDB Lookup              |
         |---------------------------------->|<------------------------------------->|
         |       [ raw_data ]                | [ jira_api.py ] (Asset Lookup)        |
         |                                   | [ enriched_data ] (Owner/System)      |
         |                                   |                                       |
         |    (4) TRANSFORM (Преобразование) |                                       |
         |---------------------------------->| [ pandas / csv_manager.py ]           |
         |   Filter: Status == "Active"      |----> [ JSON / XLSX / Split CSV ]      |
         |   Logic: Split OS vs SOFT         |                                       |
         |                                   |                                       |
         |     (5) FEEDBACK: Автопроверка    |                                       |
         |<----------------------------------| [ closure_manager/ ]                  |
         |                                   |  - discovery.py (Поиск задач и окон)  |
         | (B) PDQL проверка по ID           |  - validator.py (Аудит MP VM)         |
         | (C) Close/Reject (Status)         |  - processor.py (CSV/Actions)         |
         |                                   |  - tags_isp.py  (Управление тегами)   |

         |                                   |                                       |

         |                                   | (B) Создание Owner Tasks (SD)         |

         |                                   | [ sd_utils.py ] (Attach/Link/Assign)  |
```

## 5. Инфраструктура и Деплой
* **Хост:** `srv-isd-auto.net.billing.ru`
* **CI/CD:** GitLab Runner (автодеплой при push в `master`).
* **Cron:** Запуск ежедневно в 09:00.
```bash
0 9 * * * cd /opt/auto-maxpatrol-api && ./venv/bin/python3 main.py
```

## 6. Инструкции по поддержке
* **Новый тип отчета:** Добавить `.pdql` файл в `intergrations/jira-pdql/`.
* **Сроки алертинга:** Изменить `MAX_WAIT_DAYS` или `MAX_SUPPORT_WAIT_DAYS` в `config_jira.py`.
* **Логи:** Детальная информация в `/opt/auto-maxpatrol-api/logs/log_YYYY-MM-DD.log`.

## 8. А дальше что ? 

Сейчас «жесткая» привязка: модули в папке jira знают, что они работают именно с Jira API. Чтобы сделать систему универсальной, нужно внедрить слой Абстракции.
### Как это реализовать:
1. **Создать базовые классы (Интерфейсы):**
     * Cоздать «шаблоны» действий, которые не зависят от вендора. Например, файл base_task_manager.py, в котором прописаны пустые методы: create_issue(), get_status(), add_comment().
2. **Разделить папки по вендорам:**
     Структура modules/ примет такой вид:
     * modules/connectors/jira/ 
     * modules/connectors/naumen/ (новый код для Naumen API)
     * modules/connectors/servicenow/
3. **Использовать паттерн «Фабрика»:**
     * В main.py добавляем одну настройку в .env: TASK_TRACKER_TYPE=NAUMEN. => При запуске скрипт смотрит на эту переменную и подгружает нужный «драйвер».

### Почему это удобно для Naumen:
Для Naumen не придется менять логику validator.py (который проверяет MaxPatrol), просто новый processor.py специально под Naumen API, где вместо Jira-запросов будут использоваться методы Naumen (например, через их REST API или SOAP).
