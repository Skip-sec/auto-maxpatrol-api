# Автоматизация управления уязвимостями (MaxPatrol VM ↔ Jira) v5.0

## 1. Обзор проекта
Система реализует замкнутый цикл (**Closed-Loop**) управления уязвимостями, объединяя возможности сканера **MaxPatrol VM**, базы активов **Jira Assets (Insight)** и системы обработки заявок **Jira Service Desk**. 

**Основная цель:** Полное исключение ручного труда при рассылке отчетов владельцам систем и автоматизация контроля устранения уязвимостей на качественно новом инженерном уровне.

---

## 2. Бизнес-логика (Workflow)
Процесс разделен на быстрые ежедневные операции (контроль `User action`), автоматическую воскресную очистку зависших задач (`Waiting for support` / `Pending`) и ресурсоемкую еженедельную рассылку по понедельникам:

### 1. Ежедневный цикл (Feedback & Guard Loop)
Выполняется с понедельника по субботу для обеспечения актуальности данных и предотвращения потери задач.
* **Поиск и фильтрация:** Модуль `JiraDiscovery` собирает тикеты в статусе `User action` с помощью **одного высокоскоростного агрегированного JQL-запроса**, полностью исключая проблему N+1 сетевых вызовов.
* **Защита от закрытия (Admin Guard):**
  * Скрипт проверяет последний комментарий в каждом тикете.
  * Если обнаружено предупреждение от **Admin** о закрытии из-за отсутствия ответа (7-дневный ультиматум), проверка уязвимостей приостанавливается, а на **ISP** отправляется критический алерт.
  * **Динамический трекинг дедлайнов (Countdown Tags):** На основе даты публикации ультиматума скрипт вычисляет остаток дней и вешает на зонтичную задачу ISP соответствующую метку (`ИБ_7_дней` ... `ИБ_1_дней`), автоматически зачищая вчерашние теги.
* **Контроль регламентных автозакрытий (Regulation Guard):** Если обнаружено, что тикет закрылся системным ботом по регламенту без промежуточного ответа со стороны ИБ, на родительскую задачу ISP вешается критическая метка `SD_closed_without_answer`.
* **Интеллектуальный аудит:**
  * **Сбор данных:** Из задачи скачивается CSV, извлекаются ID уязвимостей с автоматической очисткой оперативной памяти через контекстный менеджер `with StringIO()` [1.3, 1.55].
  * **Сравнение дат (Time-Sync):** Скрипт сравнивает дату последнего сканирования хоста (`@audittime`) с датой перевода задачи в статус `User action`. Это исключает закрытие тикета на основе старых данных сканера.
* **Атомарные действия:**
  * ✅ **Автозакрытие:** Если все уязвимости исправлены, статус меняется на `Closed` (переход `61`), а сервисный комментарий передается **внутри структуры самого перехода**, что позволяет успешно проходить валидацию скрытых экранов Jira.
  * ❌ **Реджект (Return to Work):** Если найдены активные уязвимости — возврат владельцу (переход в `Waiting for support` по ID `51`) через метод `change_issue_status_with_reject`, который сначала публикует развернутый текстовый комментарий с сохранением структуры переносов строк, а затем переводит задачу.

### 2. Воскресный цикл (Biweekly Support & Pending Clean-Up)
Выполняется по воскресеньям (запуск через Cron с флагом `--biweekly`) для автоматического разбора зависших тикетов.
* **Поиск и фильтрация:** Скрипт собирает плоский список всех связанных задач в статусах `Waiting for support` и `Pending` за **один быстрый JQL-вызов**.
* **Упрощенный аудит (Без Time-Sync):** Валидация по дате последнего сканирования пропускается — проверяется только факт устранения уязвимости (`status == "fixed"`) через скачивание CSV-экспорта MaxPatrol.
* **Последовательный транзит (Workflow Chain):** Если уязвимости устранены, автоматика выполняет цепочку переходов `41 -> 61`, отправляя сервисный комментарий непосредственно внутри тела запроса для успешного прохождения экранов валидации полей Jira.

### 3. Еженедельная рассылка (Monday Action)
Запускается по понедельникам для формирования нового фронта работ.
* **Full ETL:** Полный сбор данных из MP VM по всем PDQL-запросам. Для предотвращения таймаутов СУБД используется эндпоинт **`/export`**, который за один вызов формирует легкий текстовый CSV-пакет (с таймаутом ожидания ответа до `300` секунд).
* **CMDB Enrichment:** Обогащение данных через **Jira Assets (Insight)** с использованием долгоживущих сессий `requests.Session()` (Keep-Alive пул).
* **Организация задач:** Создание главной задачи в Jira Core (**ISP**) и персональных тикетов в **Service Desk** для каждого владельца с Wiki-таблицей и прикреплением XLSX-отчетов.

## 3. Техническая архитектура
### Схема потоков данных
```text
 [ MaxPatrol VM ]              [ Python Orchestrator (Main) ]         [ Jira (Core & Service Desk) ]

        |                                    |                                      |
        |      (1) POST /assets_grid         |                                      |
        |<-----------------------------------|                                      |
        |      Token (Транзакция)            |                                      |
        |----------------------------------->|                                      |
        |                                    |                                      |
        |      (2) GET /export?pdqlToken     |                                      |
        |<-----------------------------------|                                      |
        |      CSV Stream (timeout 300s)     |                                      |
        |----------------------------------->|                                      |
        |                                    |                                      |
        |                                    | (3) CMDB Lookup (Asset Enrichment)   |
        |                                    |------------------------------------->|
        |                                    | requests.Session() (Keep-Alive Pool) |
        |                                    |<-------------------------------------|
        |                                    |                                      |
        |                                    | (4) TRANSFORM & VALIDATE             |
        |                                    | [ Pydantic v2 Models ]               |
        |                                    | [ StringIO & csv.DictReader ]        |
        |                                    |-------> Serialize: JSON/CSV/XLSX     |
        |                                    |                                      |
        |                                    | (5) FEEDBACK LOOP (Daily/Biweekly)   |
        |                                    |------------------------------------->|
        |                                    | One-Batch JQL Search                 |
        |                                    | Atomic Transitions (41 -> 61 / 51)   |
        |                                    |                                      |
        |                                    | (6) MAINTENANCE (Очистка)            |
        |                                    |-------> Purge logs/jira-pdql/ (>90d) |
```

## 5. Инфраструктура и Деплой
* **Хост автоматизации:** `***`
* **CI/CD:** GitLab Runner (автоматический деплой при push в ветку `master`). Файлы `__pycache__` и `*.pyc` принудительно исключены из синхронизации `rsync` для предотвращения конфликтов прав доступа.
* **Cron-расписание:** Запуск ежедневно в 09:00.
```bash
# Будничный запуск (DAILY MODE):
0 9 * * 1-6 cd /opt/auto-maxpatrol-api && /opt/auto-maxpatrol-api/venv/bin/python3 main.py >> /opt/auto-maxpatrol-api/logs/cron_run.log 2>&1

# Воскресный запуск (BIWEEKLY CLEAN MODE):
0 9 * * 0 cd /opt/auto-maxpatrol-api && /opt/auto-maxpatrol-api/venv/bin/python3 main.py --biweekly >> /opt/auto-maxpatrol-api/logs/cron_biweekly_run.log 2>&1
```

*Важно:* При ручном запуске скрипта из консоли сервера обязательно используйте флаг `sudo -u gitlab-runner`, чтобы не нарушать владельца генерируемых файлов логов и отчетов.
```bash
cd /opt/auto-maxpatrol-api && sudo -u gitlab-runner ./venv/bin/python3 main.py
```

## 6. Инструкции по поддержке системы
* **Новый тип еженедельного отчета:** Достаточно просто положить валидный `.pdql` файл в директорию `integrations/jira-pdql/`. Скрипт подхватит его автоматически при следующем понедельничном проходе.
* **Изменение сроков алертинга:** Параметры `MAX_WAIT_DAYS` или `MAX_SUPPORT_WAIT_DAYS` настраиваются централизованно в файле `config_jira.py`.
* **Анализ инцидентов:** Детальный лог разбора всех зонтичных задач и ответов сканера пишется в ежедневные файлы `/opt/auto-maxpatrol-api/logs/log_YYYY-MM-DD.log`.
